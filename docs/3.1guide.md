# 商品图片基础预处理脚本开发指导

## 一、任务目标

编写一个 Python 图片预处理脚本，对商品图片进行安全、可追溯的基础处理，为后续 OCR、图片分类、目标分割、代表色提取和 Hex/Lab 计算提供统一输入。

脚本只进行必要的基础预处理，不进行自动白平衡、亮度增强、饱和度增强、滤镜校正或其他可能改变商品颜色的操作。

核心原则：

1. 永远保留原始图片，不覆盖原文件。
2. 修正图片方向。
3. 检查并正确处理 ICC 色彩配置文件。
4. 将算法工作图统一为 sRGB。
5. 正确处理透明通道。
6. 计算图片哈希，用于去重。
7. 保存完整处理日志和元数据。
8. 单张图片处理失败时，不得中断整个批处理任务。

---

## 二、输入与输出

### 2.1 输入

输入为一个商品图片根目录，目录结构大概为：

```text
download_images/
├── 品牌A/
│   ├── 商品a/
|   |   ├── 图片1
|   |   ├── 图片2
│   │   └── 图片3
|   ├── 商品b/
|   |   ├── 图片1
|   |   ├── 图片2
│   │   └── 图片3
│   ...
├── 品牌B/
│   ...
└── ...
```

需要递归扫描以下格式：

```text
.jpg
.jpeg
.png
.webp
.tif
.tiff
.bmp
```

对文件扩展名大小写不敏感。

### 2.2 输出

建议输出目录：

```text
output/
├── working_images/
├── metadata/
│   └── image_preprocessing.csv
├── duplicate_groups.json
├── errors/
│   └── preprocessing_errors.csv
└── logs/
    └── preprocessing.log
```

工作图建议优先保存为 PNG，以避免重复 JPEG 压缩造成颜色漂移。

如果存储空间有限，也可以：

* 仅对需要转换的图片保存工作副本；
* 已经符合要求的 sRGB 图片只记录原始路径；
* 后续算法读取时动态处理。

## 三、推荐依赖

使用以下 Python 库：

```text
Pillow
Pillow.ImageCms
OpenCV
imagehash
numpy
pandas
tqdm
```

可选：

```text
pyvips
```

其中：

* Pillow 负责图片读取、EXIF方向修正和 ICC 色彩管理；
* OpenCV 负责后续图像算法，但不要使用 OpenCV 直接完成 ICC 转换；
* imagehash 负责 pHash、dHash 等感知哈希；
* hashlib 负责 SHA256；
* pandas 负责元数据导出。

## 四、处理总流程

每张图片严格按照以下顺序处理：

```text
读取文件
    ↓
计算原始文件 SHA256
    ↓
安全解码图片
    ↓
修正 EXIF 方向
    ↓
识别图片模式与透明通道
    ↓
读取 ICC 色彩配置文件
    ↓
判断是否需要转换到 sRGB
    ↓
正确处理透明区域
    ↓
生成算法工作图
    ↓
计算 pHash 和 dHash
    ↓
计算基本质量指标
    ↓
保存工作图和元数据
    ↓
继续处理下一张图片
```

## 五、具体处理规则

## 5.1 原始图片保护

禁止覆盖原始图片。

脚本不得：

* 修改原图片内容；
* 删除原图片；
* 重命名原图片；
* 在原目录中覆盖保存；
* 自动将原始 JPG 转成新的 JPG。

所有处理结果必须输出到独立目录。

元数据中保留：

```text
source_path
relative_path
filename
product_folder
```

---

## 5.2 计算 SHA256

在解码图片之前，对原始文件二进制内容计算 SHA256。

用途：

* 识别完全相同的文件；
* 建立稳定文件标识；
* 防止同一文件被重复处理。

示例字段：

```text
sha256
```

SHA256相同的文件属于完全重复文件。

不要立即删除重复文件，只需要记录重复关系。

---

## 5.3 图片读取与异常处理

使用 Pillow 安全读取图片。

需要处理：

* 损坏文件；
* 不完整图片；
* 不支持格式；
* 超大图片；
* 多帧 GIF 或 TIFF；
* CMYK 图片；
* 灰度图；
* 带 Alpha 通道图片。

对于多帧图片，默认使用第一帧，并记录：

```text
is_multiframe
frame_count
selected_frame
```

单张图片失败时：

* 将错误写入错误日志；
* 保存异常类型；
* 跳过当前图片；
* 继续批处理。

不得因为一张损坏图片终止整个程序。

---

## 5.4 修正 EXIF 方向

读取图片后立即执行 EXIF 方向修正。

推荐使用：

```python
ImageOps.exif_transpose(image)
```

原因：

* 某些手机图片依靠 EXIF 控制显示方向；
* 不修正会导致 OCR、目标检测和区域坐标错误。

记录字段：

```text
exif_orientation_found
orientation_corrected
```

方向修正后，后续所有宽度、高度和坐标均以修正后的图片为准。

---

## 5.5 ICC色彩配置检查

读取图片中的 ICC Profile。

建议分类为以下状态：

```text
embedded_srgb
embedded_non_srgb
profile_missing
profile_invalid
unsupported_color_mode
```

需要记录：

```text
icc_profile_present
icc_profile_name
source_color_space
color_profile_status
```

### 5.5.1 已经是 sRGB

如果图片携带有效 sRGB 配置：

```text
不进行重复色彩转换
```

只需要：

* 修正方向；
* 转换为算法需要的 RGB 模式；
* 保留颜色数据；
* 记录为 `embedded_srgb`。

### 5.5.2 有效非 sRGB 配置

例如：

```text
Display P3
Adobe RGB
ProPhoto RGB
CMYK profile
```

必须使用 ICC 色彩管理转换到 sRGB。

禁止：

* 直接删除 ICC 标签；
* 仅把图片模式改成 RGB；
* 直接把原始 RGB 数值当作 sRGB；
* 使用 OpenCV 读取后直接保存。

推荐使用：

```python
ImageCms.profileToProfile()
```

转换目标使用标准 sRGB Profile。

转换后记录：

```text
converted_to_srgb = true
working_color_space = sRGB
```

### 5.5.3 没有 ICC 配置文件

普通电商图片大量存在无 ICC 配置的情况。

处理规则：

```text
暂按 sRGB 解释，不进行数值转换
```

记录：

```text
source_color_space = unknown
working_color_space = assumed_sRGB
converted_to_srgb = false
color_profile_status = profile_missing
```

不得声称无 ICC 图片原本一定是 sRGB，只能记录为“假定 sRGB”。

### 5.5.4 ICC配置损坏

如果 ICC 配置无法读取或转换：

1. 记录 `profile_invalid`；
2. 不直接终止任务；
3. 尝试按普通 RGB 图片读取；
4. 标记为低可信工作图；
5. 设置人工复核标记。

例如：

```text
color_profile_review_required = true
```

---

## 5.6 图片模式转换

算法工作图最终统一为：

```text
RGB
8 bit/channel
sRGB 或 assumed_sRGB
```

不同模式的处理：

### RGB

按 ICC 规则处理后保持 RGB。

### RGBA

保留 Alpha 信息，不要直接丢弃。

### CMYK

如果有有效 ICC 配置，使用 ICC 转换为 sRGB。

如果没有 ICC 配置：

* 使用 Pillow 的 CMYK 到 RGB 转换作为降级方案；
* 标记 `source_color_space = unknown_cmyk`；
* 设置低置信度或人工复核标记。

### 灰度图

可以转换为 RGB，但标记：

```text
source_mode = L
is_grayscale = true
```

灰度图通常不适合作为口红代表色来源。

### 调色板模式 P

先转换为 RGBA 或 RGB，再按透明信息处理。

---

## 5.7 透明通道处理

PNG和WebP可能包含透明区域。

禁止直接使用以下方式处理：

```text
RGBA → RGB
```

因为透明像素可能被错误转换成黑色，影响后续取色。

推荐同时生成：

1. RGB工作图；
2. Alpha Mask。

字段：

```text
has_alpha
alpha_mask_path
transparent_pixel_ratio
```

处理方式：

* Alpha为0的像素标记为无效区域；
* 后续颜色提取时必须排除透明像素；
* 如果需要生成可显示的RGB图，可将图片合成到白色背景；
* 但颜色计算仍必须使用 Alpha Mask 排除透明区域。

不要把透明像素当成白色或黑色参与代表色计算。

---

## 5.8 工作图保存

建议工作图保存为 PNG。

命名建议：

```text
{sha256前16位}.png
```

或：

```text
{product_id}_{image_id}.png
```

工作图应满足：

```text
方向已修正
RGB模式
sRGB或assumed_sRGB
无自动颜色增强
无自动白平衡
无自动亮度调整
无自动对比度调整
```

如果原图片已经是：

* 方向正确；
* 有效 sRGB；
* RGB 模式；
* 无透明通道；

可以选择不生成新的工作文件，只在元数据中记录：

```text
working_image_path = source_path
working_image_reused = true
```

但后续读取模块必须保证使用相同的处理规则。

## 六、明确禁止的颜色处理

脚本不得自动执行：

```text
自动白平衡
自动曝光校正
自动对比度增强
自动饱和度增强
色温校正
色调校正
滤镜去除
去雾
美颜
锐化
超分辨率
直方图均衡化
CLAHE
Gamma校正
颜色归一化
全图亮度标准化
```

除非这些操作作为独立实验模块，并且：

* 不覆盖基础工作图；
* 单独保存；
* 明确记录处理参数；
* 不用于默认代表色提取。

基础预处理的目标是统一图片解释方式，而不是让所有图片看起来相同。

## 七、图片去重

至少实现三级去重标识。

## 7.1 完全重复

使用：

```text
SHA256
```

判断条件：

```text
SHA256完全相同
```

## 7.2 近似重复

使用：

```text
pHash
dHash
```

建议保存哈希值，不要只保存是否重复。

可设置初始阈值，例如：

```text
pHash Hamming distance ≤ 4：高度疑似重复
pHash Hamming distance 5～8：可能重复
```

阈值必须在实际数据上验证。

## 7.3 裁剪或加字版本

基础脚本可先预留字段：

```text
embedding_id
embedding_similarity
duplicate_group_id
duplicate_type
```

后续接入视觉 Embedding 模型处理：

* 裁剪图片；
* 加字图片；
* 不同分辨率版本；
* 同图不同边框版本。

去重结果只用于：

* 降低重复计算；
* 避免同一图片在商品代表色融合中被重复加权。

不得未经记录直接删除图片。

## 八、基本质量指标

基础脚本可以计算轻量质量指标，但不得修改图片。

建议字段：

```text
width
height
aspect_ratio
file_size
blur_score
mean_brightness
dark_pixel_ratio
bright_pixel_ratio
transparent_pixel_ratio
quality_warning
```

### 8.1 清晰度

可以使用 Laplacian 方差。

仅作为质量指标，不自动锐化。

### 8.2 曝光

统计：

* 亮度均值；
* 高亮像素比例；
* 暗部像素比例。

仅用于后续筛选，不自动修正亮度。

### 8.3 分辨率

记录图片尺寸。

初始可标记：

```text
短边 < 256：低分辨率
短边 256～512：中等分辨率
短边 > 512：正常
```

阈值应配置化，不要写死在业务代码中。

## 十四、验收标准

脚本至少满足以下要求：

1. 原始图片没有被修改。
2. EXIF方向能够正确修正。
3. 已是sRGB的图片不会被无意义重复转换。
4. 有有效非sRGB ICC的图片能够正确转换到sRGB。
5. 无ICC图片被标记为 `assumed_sRGB`。
6. 透明像素不会被当作黑色参与后续颜色计算。
7. CMYK图片有明确处理和标记。
8. 每张图片都有SHA256。
9. 每张有效图片都有pHash和dHash。
10. 单张图片失败不会中断整个任务。
11. 所有处理操作均有日志和元数据。
12. 不执行任何自动颜色增强。
13. 工作图可被后续OpenCV、OCR和分割模块直接读取。
14. 重复运行时具有幂等性，不会反复生成重复文件。
15. 输出结果可以追溯到原始图片。

## 十六、最终处理逻辑摘要

脚本应实现以下决策逻辑：

```text
图片已是有效sRGB
→ 修正方向后直接作为工作图使用

图片带有效非sRGB ICC
→ 通过ICC色彩管理转换到sRGB

图片没有ICC
→ 暂按sRGB解释，并记录profile_missing

图片ICC损坏
→ 降级读取并标记人工复核

图片带透明通道
→ 保留Alpha Mask，透明像素不参与颜色计算

图片为CMYK
→ 优先使用ICC转换，无ICC时降级转换并标记

所有图片
→ 计算SHA256、pHash、dHash
→ 记录尺寸和基本质量
→ 不覆盖原图
→ 不进行颜色增强
```

该脚本的职责仅是建立统一、可靠、可追溯的算法输入。它不负责提取最终代表色，也不负责修正不同拍摄光源和商家滤镜造成的颜色差异。
